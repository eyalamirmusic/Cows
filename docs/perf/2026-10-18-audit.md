# Performance audit, 2026-10-18

Branch `perf` in `~/projects/Cows-perf`. Every claim below comes with the
measurement behind it; each number names the commit it was measured on.

The branch was rebased twice while the audit ran: onto `cb88936`, then onto
`ca3d7c3` (the barn). The hashes the numbers name are the commits as they were
then built:
- `ad564da`: `566cf1b` plus tooling
- `fe95712`: the 60 fps cap
- `bcb0e8a`: the frame-rate setting plus the input-owner log, on `cb88936`

`ad564da` and `fe95712` have the same app code as `566cf1b` (+ cap). Their
equivalents on the branch now are `f97763c` and `516e3c3`.

## Machine and builds

- MacBook Pro Mac17,7, Apple M5 Max (18 CPU cores, 40 GPU cores), 128 GB,
  macOS 26.5.1 (25F80). Built-in Liquid Retina XDR, 120 Hz ProMotion; every run
  on that display.
- Release (`build-release`, `-DCMAKE_BUILD_TYPE=Release`) for every number;
  RelWithDebInfo (`build-relwithdebinfo`) for call stacks only. eacp pinned at
  `af7b7037` (CPM, `develop` at configure time); `build-release-eacp` builds
  against `~/projects/eacp` at `text-face-lookup` (`356026fb`) for the eacp
  experiment.
- The machine was not idle: other sessions, VMs and Jamie were using it. Runs
  wait out any other Cows process (`perf.sh`), and GPU time was coordinated in
  iac `#cows-gpu`.

## Protocol

`tools/perf.sh <scenario> <label> [runs]` launches a fresh process per run at
`COWS_SEED=3 COWS_WINDOW=1280x800 COWS_QUALITY=high COWS_PROFILE=1`, and
`COWS_FPS=auto` unless told otherwise. After a warm-up it measures a window:

- the process's CPU seconds per second (total, user, system, main thread, the
  rest), from `proc_pid_rusage` and per-thread `proc_pidinfo`
- the energy the kernel bills the process (`ri_energy_nj`, as W)
- wakeups per second and footprint
- `top`'s %CPU and POWER
- the GPU's device utilisation (`ioreg`)
- the mean of `COWS_PROFILE`'s once-a-second lines: fps, frame interval and
  p95, CPU ms per part, GPU ms per frame and per pass

Scenarios:

| | env | warm-up / window |
|---|---|---|
| S1 menu idle | — | 5 s / 30 s |
| S2 editor open | `COWS_DRESS=1` | 5 s / 30 s |
| S3 play, standing | `COWS_MENU=0` | 5 s / 15 s |
| S4 play, walking | `COWS_MENU=0 COWS_WALK=1` | 5 s / 15 s |
| S5 ending | `COWS_FOUND=1` | 1 s / 3 s (it loops at 4.5 s) |

A run is thrown away and repeated when:

- another Cows is running
- the process died
- it drew no frames: one S2 run on `ad564da` logged nothing at all
- it changed screens in the window: the app now logs `Cows: input to <owner>`,
  and `perf.sh` rejects any run that logs one inside its window.

The window takes key focus. Of the 10 S1 runs on `fe95712`, two left the menu
(one in its first seconds, one 7 s into the window), and three of the 10
earlier S1 runs on `ad564da` did too. Their profile lines show the menu text
vanishing and the scene count jumping at the moment fps changes. With the guard
on, 4 of the 40 S1/S2 runs on `bcb0e8a` were caught and rerun.

Statistics come from `tools/perf-stats.py`: mean ± 95% CI, Welch's t p, Cohen's
d, and Mann–Whitney U p as the non-parametric check. A fix is kept only at
p < 0.01 with a meaningful effect.

Call stacks: `tools/perf-sample.sh` runs `sample <pid> 20` on 3 launches per
scenario of the RelWithDebInfo build (`ad564da`).
`tools/perf-sample-top.py` keeps the samples that were on the CPU and reports
inclusive shares. Those are per-mille-level estimates of where the main thread
spends its time, not timings.

## Hot paths (proven)

Shares are inclusive, as a percentage of the main thread's on-CPU samples. The
main thread is 28.5% (S1), 49.0% (S2), 30.9% (S3), 35.0% (S4) and 18.4% (S5) of
the process's on-CPU samples.

The rest of the process's on-CPU samples are Metal's command-buffer submission
on workqueue threads: `_dispatch_source_invoke → -[_MTLCommandQueue
_submitAvailableCommandBuffers] → IOGPUCommandQueueSubmitCommandBuffers` is
37–43% of the process. It is paid once per frame.

Stacks behind the large ones:

- **Shadow pass encoder:**
  `renderNow → CowsView::render → drawShadows → Frame::beginPass →
  -[AGXG17XFamilyCommandBuffer renderCommandEncoderWithDescriptor:]`.
  `beginPass` is 13.8% of main in S3, and the encoder creation inside it is
  almost all of that. The scene pass's `beginPass` is 3.4%.
- **Culling:** `drawBatch → instanceInView → boxInView`, 6.9% of main in S3.
- **Text in the editor:** in S2, `CowsApp` HUD lambda → `Editor::draw →
  drawRow → drawLabel → drawMenuText → TextRenderer::layout →
  GlyphAtlas::findOrAddFace` (5.2% self, plus `_platform_memcmp` 2.4%). It is
  a linear scan of every face with a string compare.

### (a) Does the app render every refresh when idle in the menu?

Yes, at `566cf1b`/`ad564da`.

- `CowsView` calls `setContinuous(true)`, and never `setMaxFps`.
- In eacp `af7b7037`, `GPUView-Apple.mm` `startContinuous()` builds a
  `Threads::DisplayLink` (CVDisplayLink) whose tick is
  `view.update(time); view.renderNow();`. It is driven on the main queue
  through `dispatch_async`.
- `GPUView::setMaxFps` exists, but it is 0 (uncapped) unless set. There is no
  render-on-demand while continuous.
- Measured: S1 120.0 fps, frame 8.33 ms, the CVDisplayLink thread at 1.8 ms
  CPU/s, GPU 369 ms busy per second.
- The cap eacp offers is a skip inside the tick: the link still wakes the
  process at every refresh. The CVDisplayLink thread costs 2.4 ms/s with the
  60 fps cap, against 1.8 ms/s uncapped.

### (b) Shares of the main thread

Culling (`instanceInView`/`boxInView`) is 5–7%. The grass plan and draw are 1–3%.

HUD text:
- S1: `Menu::draw` 5.9%, of which `drawMenuText` (16 outline passes per label)
  is 3.7%.
- S2: `Editor::draw` 18.1%, of which `drawMenuText` is 14.1% and
  `TextRenderer::layout` 16.4%. Within layout, `findOrAddFace` is 8.0%.

The shadow pass is 19–27%, mostly the driver's encoder creation (above). As
shares of the whole process, all of these are 2–4%, except S2's text at about 8%.

### (c) Per-frame allocations

`malloc`/`free` frames are 3.3–4.6% of the process's on-CPU samples. The
nearest of our callers:

- eacp's `GPUView::renderNow` (117/288 samples in S1), and the
  `DisplayLink::Native` dispatch block (86/288): eacp's per-frame objects and
  the `std::function`/block hop
- `GlyphAtlas::shape` and `TextRenderer::layout` in S2

Cows code itself allocates little per frame. `visible` and the batches are
reused.

### (d) Audio while idle

The MakeASound recovery thread uses 0.03 ms of CPU a second. Measured with
`proc_pidinfo` by thread id, matched to `sample`'s `Thread_<id>`: it wakes on a
250 ms watchdog (`kWatchdogInterval`). `sample` showed it at 14–17% of on-CPU
samples. That was sleeping threads caught inside `_pthread_cond_wait →
__gettimeofday`, and `perf-sample-top.py` now counts those as waiting.

The CoreAudio IO thread uses 2.2–3.1 ms/s.

### (e) GPU per pass and utilisation against fps

- Per pass, at 120 fps: shadows 0.13–0.8 ms, scene 2.0–2.9 ms (table above).
- `ioreg` utilisation is 64–71% in every scenario. It counts the whole GPU,
  compositor included, at whatever clock DVFS has picked.
- Halving the frame rate (S1/S2, below) raises GPU ms per frame by 44–46%: the
  GPU clocks down. GPU busy time per second falls 28%, while `ioreg`
  utilisation falls only 5–7% (p = 0.045 and 0.012). Read GPU savings from busy
  ms/s, not from utilisation.

## Fixes

### 1. Frame rate as a setting, Auto capping the menus at 60

Commits `f97763c` (cap), `df1ea79` (setting, `COWS_FPS`), `a220855` (perf
scripts pin it) and `516e3c3` (input-owner log), as they stand after the rebase
onto `ca3d7c3`. Measured on `bcb0e8a`, which is `516e3c3` before that rebase
(on `cb88936`).

- **Hypothesis:** the menu and the editor redraw a nearly still scene at
  120 Hz. Capping them at 60 halves the GPU and per-frame CPU work there.
- **Fix:** `FrameRate { Auto, Sixty, Max }`, saved in `settings.json` as an
  enumerator name, with unknown names loading as Auto. Settings has a second
  row, "Frame rate: Auto / 60 / Max", applied at once.
  `CowsView::paceFrames` hands `maxFramesPerSecond(rate, menusHaveInput)` to
  `GPUView::setMaxFps` each update:
  - Max: every refresh
  - 60: everywhere
  - Auto: 60 while the menu or editor owns input and no swing is running,
    every refresh otherwise
  `COWS_FPS=auto|60|max` overrides it.
- **Predicted:** fps −50%, CPU −40–50%, GPU busy time −50%.
- **Visual:** a single frame is unchanged. The cap only changes how often
  frames are drawn; `render()` is untouched, and snapshot tests pass. CowsArt
  renders off-screen, not through the display link, so its output cannot
  change.
- **Frame pacing under Auto:** 60.00 fps, frame 16.67 ms, p95 17.5 ms, p99
  median 17.6 ms. In S1, 19 of 300 seconds held one 25 ms frame (a third tick
  skipped); in S2, none did. See the eacp issues below.

Before is `COWS_FPS=max`, after is `COWS_FPS=auto`. Same binary, `bcb0e8a`,
n = 10 × 30 s each:

### Not attempted (measured share below the bar)

The bar was ≥ 5% of the scenario's CPU, or ≥ 10% of frame time.

- `normalMatrixFor` → `Mat4::inverted`, once per dynamic instance per frame:
  3.6–6.8% of main, about 2% of process CPU. A cheaper normal matrix also
  changes float results, so the output would not be byte-identical.

  the process.

## eacp issues (with evidence)

1. **`GlyphAtlas::findOrAddFace` scans every face with a string compare.** It
   is 8.0% of the main thread in the editor. Fixed on `text-face-lookup`;
   measured above (HUD −31%, p = 0.004).
2. **`DisplayLink::setMaxFps` paces by when the tick reaches the main thread,
   not by vsync count.**
   - At 60 on a 120 Hz panel, S1 held one 25 ms frame (three refreshes) in 19
     of 300 seconds.
   - `rateLimited` in `DisplayLink.cpp` accumulates `steady_clock` time between
     main-queue arrivals, with a half-period tolerance, so dispatch jitter can
     skip a third tick.
   - Counting refreshes when the refresh rate divides evenly (or using the
     CVDisplayLink output time) would hold 2:2.
3. **The cap still wakes the process at every refresh.** The CVDisplayLink
   thread costs 2.4 ms/s with the cap, against 1.8 ms/s uncapped. On macOS
   14+, `CADisplayLink` with `preferredFrameRateRange` (or `NSView`'s display
   link) would let the system stop waking the process.
4. **Shadow pass encoder creation is expensive.** `Frame::beginPass →
   renderCommandEncoderWithDescriptor:` is 13.8% of main in S3 for the
   shadow pass, against 3.4% for the scene pass. The cause is not proven: the
   R32Float plus depth target's load and store actions, or texture residency.
   This needs a Metal System Trace (not taken).
5. **Per-frame allocations in `GPUView::renderNow` and the `DisplayLink` block**
   are about 2.7% of the process's on-CPU samples in S1.
